# Безопасность InTrAvia

Документ описывает текущее состояние защиты прототипа и обязательные шаги перед
любым публичным запуском. Прототип создавался как демонстрационный стенд для
соревнования и **не является production-ready**.

Обновлено: 2026-11-23.

## Как включить защиту

```bash
# .env или окружение
SECRET_KEY=<64 hex-символа>
AUTH_REQUIRED=1
SESSION_COOKIE_SECURE=1   # только если сервер работает по HTTPS
CORS_ORIGINS=             # пусто = same-origin
```

При `AUTH_REQUIRED=1`:

- все `/api/*`, кроме `/api/auth/login`, `/api/auth/logout` и контракта
  трекинга `/api/v1/track|stream|agents|snapshot`, требуют сессию — иначе 401;
- изменяющие маршруты `/api/mcc/*`, `/api/cpu/*`, `/api/dispatcher/*`,
  `/api/pilot/*`, `/api/engineer/*`, `/api/users*`, `/api/v1/import/*`,
  `/api/clear_all*` доступны только своей роли или `admin` — иначе 403;
- дашборды без сессии перенаправляют на `/login.html`, чужая роль — на свой
  дашборд;
- куки сессии: `HttpOnly`, `SameSite=Lax`, срок 12 часов, `Secure` по флагу.

**Важно:** мобильные WebView-приложения (`/m/engineer`, `/m/agents`) рассчитаны
на доверенную локальную сеть. При `AUTH_REQUIRED=1` их страницы открываются, но
API-вызовы без сессии получат 401 — экран входа в приложениях пока не реализован.
Для полевого использования либо оставляйте стенд в закрытой сети, либо
доработайте вход в мобильных страницах.

## Что ещё критично

1. **История git.** `SECRET_KEY` из коммита `8ea97c8` и прежние открытые пароли
   остаются в истории публичного репозитория. Сменить ключ и пароли, затем
   вычистить историю (`git filter-repo --path .env --path database.db --invert-paths`)
   или пересоздать репозиторий.
2. **`database.db` в репозитории.** Пароли теперь scrypt-хэшами, но ФИО, телефоны
   и демо-учётки опубликованы. Заменить файл обезличенным seed-скриптом: без
   `database.db` приложение не стартует (`init_db()` только валидирует схему).
3. **Cloudflare Tunnel без авторизации.** `host_public.ps1` публикует приложение
   в интернет. Запускать только с `AUTH_REQUIRED=1` и Cloudflare Access, либо не
   запускать вовсе.

## Остаточные риски

4. **XSS в дашбордах.** В `mcc`, `admin`, `dispatcher`, `pilot`, `cpu` и
   `engineer` активно используется `innerHTML` (10–31 вхождение на страницу).
   Часть полей экранируется, покрытие неполное. Мобильные страницы `/m/engineer`
   и `/m/agents` экранируют все вставки через `esc()`.
5. **HTTP в WebView.** `usesCleartextTraffic="true"` и произвольный адрес
   сервера: возможен MITM в открытой сети. Для поля — HTTPS-туннель.
6. **Fallback `SECRET_KEY`.** Без переменной окружения генерируется случайный
   ключ на процесс (не предсказуемый), но сессии сбрасываются при перезапуске.
7. **Лимит тела 64 МБ и отсутствие общего rate limiting.** Возможен DoS.

`test_pilot_atlb` помечены `skip`: они описывают удалённую архитектуру

текущую модель либо удалить.

## Что сделано правильно

- SQL-запросы параметризованы; динамические фрагменты строятся из whitelist.
- Загрузки файлов отсутствуют — path traversal не применим.
- WebView: отключены file/content access, `allowFileAccessFromFileURLs`,
  `allowUniversalAccessFromFileURLs`, сохранение паролей; внешние ссылки
  открываются в браузере.
- `.env` снят с отслеживания, добавлен `.env.example`.
- Все пользователи переведены на хэши (`tools/migrate_passwords.py`).
- Работает на `debug=False`.
