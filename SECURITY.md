# Безопасность InTrAvia

Документ описывает текущее состояние защиты прототипа и обязательные шаги перед
любым публичным запуском. Прототип создавался как демонстрационный стенд для
соревнования и **не является production-ready**.

Обновлено: 2026-11-23.

## Кратко

| Область | Состояние |
|---|---|
| Аутентификация API | ❌ отсутствует |
| Авторизация по ролям на сервере | ❌ отсутствует |
| Хранение паролей | ❌ открытый текст |
| CORS | ❌ `origins: "*"` для всех маршрутов |
| Секреты в репозитории | ⚠️ `.env` больше не отслеживается, но остался в истории |
| `database.db` в репозитории | ⚠️ отслеживается, содержит демо-пароли и данные |
| Тесты безопасности | ❌ не проходят (устарели) |
| WebView-приложения | ⚠️ HTTP разрешён, доступ к файлам отключён |
| SQL-инъекции | ✅ параметризованные запросы, whitelist для динамического SQL |

## Критично

1. **Нет серверной аутентификации.** `/api/auth/login` проверяет пару
   email/пароль и возвращает профиль, но не создаёт сессию. Все ~92 маршрута,
   включая диспетчерские, MCC- и административные, доступны без входа.
   Любой, кто видит сервер, может менять заявки, маршруты и справочники.
2. **Публичный репозиторий с секретами.** `database.db` и ранее `.env`
   хранились в git. В базе — открытые пароли демо-пользователей (включая
   администратора), в истории коммитов — `SECRET_KEY`. Считать эти данные
   скомпрометированными: сменить ключ и пароли, вычистить историю
   (`git filter-repo`) или пересоздать репозиторий.
3. **Публикация через Cloudflare Tunnel без авторизации.** `host_public.ps1`
   выставляет приложение в интернет по случайному HTTPS-адресу. Без
   аутентификации это полный удалённый доступ к системе.

## Высокий риск

4. **CORS `*` + отсутствие auth.** Любой сайт, открытый в браузере оператора,
   может отправлять запросы к API и читать ответы. Фактически это CSRF с
   эксфильтрацией данных.
5. **Пароли в открытом виде.** Сравнение `WHERE email=? AND password=?`,
   без хеширования, без ограничения попыток входа и блокировок.
6. **Устаревшие тесты безопасности.** `tests/test_security.py` рассчитан на
   прежнюю архитектуру и падает (20 ошибок в `conftest.py`), поэтому защитные
   свойства никем не проверяются.

## Средний риск

7. **XSS в дашбордах.** В `mcc`, `admin`, `dispatcher`, `pilot`, `cpu` и
   `engineer` активно используется `innerHTML` (10–31 вхождение на страницу).
   Часть полей экранируется, но покрытие неполное. Мобильные страницы
   `/m/engineer` и `/m/agents` экранируют все вставляемые данные через `esc()`.
8. **HTTP в WebView.** `usesCleartextTraffic="true"` и произвольный адрес
   сервера: трафик можно перехватить в незащищённой сети. Для полевого
   использования — только HTTPS-туннель.
9. **Fallback `SECRET_KEY` в коде.** Если переменная окружения не задана,
   используется предсказуемая строка.

## Низкий риск

10. Лимит загрузки 64 МБ и отсутствие rate limiting — возможен DoS/заполнение диска.
11. Три обработчика возвращают `str(e)` клиенту — утечка внутренних деталей.

## Что уже сделано правильно

- SQL-запросы параметризованы; динамические фрагменты строятся из whitelist.
- Нет эндпоинтов загрузки файлов — path traversal не применим.
- WebView: отключены file/content access, `allowFileAccessFromFileURLs`,
  `allowUniversalAccessFromFileURLs`, сохранение паролей; внешние ссылки
  открываются в браузере, а не внутри WebView.
- `.env` снят с отслеживания, добавлен `.env.example`.
- Работает на `debug=False`.

## План исправления (по приоритету)

1. Ввести серверные сессии (`session['user_id']`) и декоратор
   `login_required(role=...)` на все `/api/*`, кроме `/api/auth/login`.
2. Перевести пароли на `werkzeug.security` (PBKDF2/bcrypt), добавить
   rate limiting входа.
3. Ограничить CORS конкретным origin, включить SameSite-cookie и CSRF-токены.
4. Ротировать `SECRET_KEY`, удалить секреты из истории git.
5. Заменить `database.db` в репозитории на обезличенный seed-скрипт.
6. Починить или переписать `tests/test_security.py`, добавить проверки
   401/403 на каждый защищённый маршрут.
7. Провести аудит `innerHTML` в дашбордах и перейти на `textContent`/экранирование.
8. Для публикации — reverse proxy с TLS и аутентификацией, не открывать
   Flask/waitress напрямую.
